# Stage B guide: sharing multiplayer sessions through EOS lobbies

This is for a developer joining the project. It describes **what** has to be written and where it goes. It is a scope, not an implementation.
Read [`HANDOFF.md`](HANDOFF.md) first (sections 3, 4.7, 4.8, 6 and 8), then the "Xbox-free mode" part of [`EOS_PLAN.md`](EOS_PLAN.md).

## Background in one paragraph

Phantom Dust (2017, Microsoft Store) did matchmaking through Xbox Live's session directory (MPSD) via the XSAPI WinRT library.
pdnet is a DLL shipped in place of `Microsoft.Xbox.Services.dll`. In Xbox-free mode (`pdnet.ini: xbox=off`) it implements every
`Microsoft.Xbox.Services.*` class itself. **Stage A** (done) keeps sessions in an in-memory store on one PC, so creating a match works but no one else can see it.
**Stage B** (this job) backs that store with Epic Online Services lobbies so players on different PCs can find and join each other's sessions.
In-match traffic (stage C) is out of scope; it already runs over pdnet's direct UDP (LAN or port-forwarded).

## What you start with

| Piece | Where | State |
|---|---|---|
| EOS platform thread, device-ID sign-in (no Epic account), re-sign-in | `pdnet/src/eos.cpp`, `eos.h` | Works in game (75 min soak). Use `eos::Post()` for every EOS call. |
| EOS SDK loaded at run time | `pdnet/src/eossdk.cpp`, `eossdk.h` | Loads `EOSSDK-Win64-Shipping.dll` (SDK 1.19.2) by function pointer. You will add the lobby functions here. |
| Credential store for the sandbox | `pdnet/src/credstore.cpp` | Works. Don't touch. |
| Session model and store | `pdnet/xsapi/mpsd.h`, `mpsd.cpp` | `SessionDoc`, `MemberDoc`, `SessionStore` (in memory). **This is the main file you change.** |
| XSAPI stand-in classes | `pdnet/xsapi/stubs/Multiplayer.*.cpp` | Generated by `xsapi/generate.py`. Unimplemented members log `xsapi-stub:` and return defaults. A file with a `// pdnet-hand` line is never regenerated. |
| Feasibility proof that lobbies work in the sandbox | `pdnet/src/eostest.cpp` | Created and deleted a lobby in game. Useful as a reference for loading and calling the lobby interface. |

## Setup

1. Your own copy of the game (unpacked UWP dump; no game files are shared) and Developer Mode on. Install the mod with the test kit (`testkit/`), or follow HANDOFF §3 on this PC.
2. Visual Studio 2022 with C++ tools, Windows SDK 10.0.22000, Python 3.10.
3. EOS SDK 1.19.2 (C SDK) from the Epic developer portal, for headers and the samples. Ask the project owner for a **dedicated client** (product/sandbox/deployment ids, client id and secret) in an `eos.ini`. Never commit it.
4. Generate the XSAPI stand-in once: `py -I pdnet\xsapi\generate.py <game>\Microsoft.Xbox.Services.winmd`.
5. Build into a new folder: `pdnet\build.cmd build-stageb` (never into `build` or `build-stage2-1226`, which are known-good copies).
6. Install the DLL into a **test build folder** (HANDOFF §3 explains the build folders; don't overwrite the owner's Teredo build), set `xbox=off eos=on display_name=<name>`, register it, play, then read `xboxfree.ps1 -Report` and `pdnet.log`.

## Step by step

### Step 1. Extend the SDK loader

Add the EOS Lobby interface functions you need to `eossdk.*`, in the same style as the existing ones (resolved at load, null-checked, logged if missing).
You'll need at least: get the lobby interface from the platform; create, join, leave, destroy; lobby search (create search, set parameters, find, read results);
lobby and member modification (attributes, permission level, max members); copy lobby details and read attributes/members;
and the notifications for lobby updates, member updates and member status. The SDK's lobby sample shows all of these.

**Done when:** the DLL builds and logs that every lobby function resolved.

### Step 2. Define the lobby ↔ session mapping

Write this down in `mpsd.h` comments before coding. Proposed mapping (adjust after reading what the game actually writes):

| Session field (`SessionDoc`) | EOS lobby |
|---|---|
| `Key()` = scid + template + session name | A lobby attribute (e.g. `PD_KEY`), searchable. Keep a `key -> EOS lobby id` map. |
| `maxMembers` (4) | Lobby max members |
| `visibility`, `joinRestriction`, `closed` | Permission level (public / join via presence / invite-only) plus an attribute for `closed` |
| `customConstantsJson` | Lobby attribute (set once at create) |
| `customProperties` (name -> JSON) | One lobby attribute per property, or one JSON attribute if limits force it |
| `keywords`, search handle metadata | Searchable lobby attributes (step 5) |
| `hostDeviceToken` | Lobby attribute (owner-written) |
| `changeNumber` | Incremented locally on every remote update (step 6) |

| Member field (`MemberDoc`) | EOS lobby member |
|---|---|
| `xuid` | The member's EOS product user id (pdnet already uses its own stable id; pick one and keep it consistent) |
| `gamertag` | Member attribute `PD_NAME` (`display_name`) |
| `deviceAddressBase64` | Member attribute `PD_ADDR` (pdnet's 34-byte snapshot, Base64) |
| `customConstantsJson`, `customProperties` | Member attributes |
| `status`, `joinTime`, `initializeRequested` | Member attributes or local bookkeeping |
| `memberId` | Assign deterministically (e.g. order of join), so every PC numbers members the same way |

Check the SDK documentation for attribute key length, value length and attribute count limits. If the game's JSON blobs are too large, store them compressed or split.

**Done when:** the table is in the code comments and you've confirmed from a stage A log what properties the game actually writes (enable logging in `mpsd.cpp`).

### Step 3. Make `SessionStore` EOS-backed (create, write, delete)

`SessionStore::Write()` is the single place every session write goes through, which is why it's the integration point.

- New session (`created`): create the EOS lobby, set the lobby attributes, set this PC's member attributes, store the lobby id.
- Existing session: diff the written `SessionDoc` against the stored copy, push only session-level changes (if this PC owns the lobby) and this PC's own member entry.
- Member `leaving` / session `deleted`: leave the lobby (or destroy it if the owner leaves and the game expects the session to end; check the game's behaviour).
- Keep the in-memory copy as a cache. Return it immediately as stage A does, and update it when EOS confirms.

**Threading.** EOS calls and callbacks run only on the EOS thread (`eos::Post`). The XSAPI async methods are C++/WinRT coroutines on the game's threads.
Bridge them with a completion (promise/event) so the coroutine waits for the EOS callback without blocking the EOS thread. Never call back into the game from the EOS thread while holding `m_lock`.

**Done when:** creating a match in game creates a lobby that the Epic dev portal or a second test client can see, with correct attributes, and the stage A behaviour (lobby screen appears) is unchanged.

### Step 4. Join and read

- `MultiplayerService` read/get-session calls: if the key maps to a remote lobby, return a `SessionDoc` built from the EOS lobby details (copy details, read attributes and members).
- Joining (the write that adds this PC's member to someone else's session): join the EOS lobby, then set this PC's member attributes.
- Fill `MemberDoc.deviceAddressBase64` from `PD_ADDR`; stage 2 networking (`net.cpp`) uses it to open the in-match UDP link.

**Done when:** PC 2 can join PC 1's lobby by key (hard-code the key for this test) and both `pdnet.log` files show the other member.

### Step 5. Search handles and the lobby browser

Stubs to implement (in `xsapi/stubs`, mark each file `// pdnet-hand`):

- `MultiplayerService::SetSearchHandleAsync(MultiplayerSearchHandleRequest)`: copy its `NumbersMetadata`, `StringsMetadata` and tags into searchable lobby attributes. Store a search handle id on the session.
- `MultiplayerSession::SearchHandleId`: return it.
- `MultiplayerService::GetSearchHandlesAsync(MultiplayerQuerySearchHandleRequest)`: run an EOS lobby search filtered on those attributes; build `MultiplayerSearchHandleDetails` for each result (session reference, member counts, metadata, handle id).
- `ClearSearchHandleAsync`, if the game calls it (check the stub log).

Look at the game's filter strings in the log; it may query on specific metadata keys (game mode, version). Map only what the game uses.

**Done when:** the game's lobby browser on PC 2 lists PC 1's lobby, and choosing it joins (step 4).

### Step 6. Change notifications

- Register for EOS lobby update, member update and member status notifications on the EOS thread.
- On each one: rebuild the cached `SessionDoc`, bump `changeNumber`, work out the `MultiplayerSessionChangeTypes` (members, properties, host, etc.) and raise `MultiplayerService::MultiplayerSessionChanged` with a `MultiplayerSessionChangeEventArgs` (session reference, branch, change number), respecting `subscribedChanges`.
- Implement `MultiplayerService::CompareMultiplayerSessions(a, b)` (or the static on `MultiplayerSession`, whichever the game calls) to return the change types between two snapshots. Use the same diff function as above.
- Raise `MultiplayerSubscriptionLost` if EOS signs out or the lobby is lost.

**Done when:** on PC 1, the lobby screen shows PC 2 arriving and leaving without a restart.

### Step 7. Remaining lobby calls

- `MultiplayerService::SetActivityAsync`: likely a no-op success is enough (it sets Xbox presence). Optionally mirror to EOS presence later.
- `MultiplayerSession::DateOfNextTimer`: return "no timer" (default DateTime) unless the log shows the game depends on it.
- Anything else `xboxfree.ps1 -Report` lists during a two-player lobby → match → return-to-lobby cycle.

### Step 8. Robustness

- EOS re-sign-in (already in `eos.cpp`) must re-join or rebuild lobbies, or report the session as lost.
- Lobby owner leaves: decide between host migration (EOS supports owner promotion) and ending the session; check what the game's MultiplayerManager expects from `HostDeviceToken` changes.
- Timeouts on every bridged call so the game never hangs on a lost callback (this game hangs forever on async calls that never finish; see the Connected Storage note in HANDOFF §4).
- Version gating: add a searchable `PD_VERSION` attribute so different mod versions don't see each other.

## Test plan

1. **One PC:** create match → lobby visible to a second EOS client (a small console tool built from the SDK sample with its own device id is enough).
2. **Two PCs, same LAN:** browse → join → both see each other → start match (in-match uses direct UDP, which works on a LAN) → leave → rejoin.
3. **Two PCs, different networks:** lobby part should work; the match itself will only connect with port forwarding until stage C.
4. Soak: lobby open 30+ minutes, through an EOS token refresh.
5. Regression: `xbox=on` and `network_mode=teredo` still behave exactly as before (the owner plays online with the Teredo build).

## Rules of the project

- Never commit `eos.ini` / `eos.local.ini` or any game files.
- Don't modify the master dump or the Teredo build folder.
- Build into new folders, commit before risky changes, and record findings in `HANDOFF.md`.
- Players need no Epic account and no router changes; keep device-ID login.
